# Owner exercises (spec Part K, tracked separately from assistant-built work)

Generated code never counts as the owner's demonstrated understanding. This log records the owner's own answers to
the end-of-milestone exercises (K.1) and, later, the K.2 exercises and the K.3 assessment. Requirement PERS-01.

| Milestone | Exercise | Owner's answer (summary) | Assessment |
|---|---|---|---|
| 1 | With `AI_PROVIDER=anthropic` and no key, why does preflight say NOT READY instead of falling back to mock? | A silent fallback would make mock answers look like live results and break the "never describe mock as live" rule. Failing loudly with the exact missing settings lets the operator fix the configuration, and nobody is misled about which model produced an answer. (2026-10-28) | Correct and complete: names both the honesty rule (spec B.2, E.5) and the operational benefit |
| 2 | Why is D21 (corporate exception buried in policy text) predicted to be fixed by B, not C? | The exception is a fixed, findable rule (`CORP*` rate codes on travel-agent bookings); once it's in the rules engine and indexed, a deterministic check handles it every time. AI helps where the input is messy or unpredictable, not where a stable rule is badly documented. (2026-10-28) | Correct: states the core principle that stable rules belong in the rules engine |
| 3 | Why does the labeler refuse to label a pending posting under policy v1, and what would you do if a real customer's v1 had no pending rule? | Policy v1 has no rule, so any label would be invented; refusing is the same "fail loudly instead of silently assuming" principle as preflight. For a real customer: ask the policy owner how those cases were actually handled, record the answer as a dated, approved policy clarification, then label those cases and flag them as decided by clarification. (2026-10-29) | Correct and complete: adds the governance step (a dated, approved clarification) a real engagement needs |
| 4 | Why does the mock API credit two different idempotency keys for the same stay, and whose job is it to stop that? | Real customer systems usually deduplicate only by idempotency key, not by business meaning, so the mock deliberately credits two different keys for the same stay to behave like a real platform. Preventing two cases from crediting one stay is the job of our own write path (approval binding, ledger re-check before execution, duplicate check across cases), not the upstream system's. (2026-10-29) | Correct and complete: separates the platform's guarantee (one effect per key, ADR-0039) from the business guarantee (one credit per stay) and puts the second in the app's write path, which is where Milestones 5–6 build it (ADR-0044) |
| 5 | What would happen to the benchmark's D07 result if the shared duplicate check also netted re-posts by stay, and why is that a problem even though it sounds safer? | The shared write path would quietly fix D07 (reversed and re-posted transactions) for every arm, including legacy, so arm A would look correct on D07 and the benchmark would credit the write path instead of the arm that actually understands the ledger. That contaminates the pre-registered comparison and mixes ledger interpretation into a safety layer whose only job is preventing duplicate effects of our own writes. (2026-11-03) | Correct and complete: names both the measurement harm (a pre-registered prediction silently invalidated) and the design harm (a safety layer taking on business interpretation), as ADR-0044 does |
| 6 | A same-key retry after a confirmed absence works. If the attempts ran out, the approval expired and a new request created a new key, why is the same-key retry safe while the new-key path isn't, and what would you ask a real vendor to size that risk? | A same-key retry is safe because the vendor deduplicates by key: if the first attempt landed late, resubmitting with the same key returns the existing adjustment, so nothing is credited twice. A new key is a new operation, so if the original attempt commits after our settle window, both credits land, and our local one-credit-per-stay rule can't see a commit we don't know about. Questions for the vendor: the maximum delay before a committed adjustment appears in status lookups, how long keys are retained, whether lookups are consistent right after a write, whether timed-out submissions can still be applied later, and whether they offer a business-level duplicate check per stay or a reversal API. (2026-11-05) | Correct and complete: separates the platform's guarantee (one effect per key) from what the app can see, and names why the local index can't help. It goes beyond the RFC's open questions by asking whether a timed-out submission can still apply, and for a per-stay check or a reversal API, both of which would change the design (RFC-0001, risks) |
